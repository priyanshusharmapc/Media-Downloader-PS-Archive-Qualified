# MDPS-AUDIT2-025: committed state and generated-report outcomes

The authoritative transaction and its generated reports have separate outcomes.
Reconciliation returns `committed=true` as soon as registry and history writes
have committed, with accurate observed/active/removal counts even when a report
cannot be rebuilt. `projectionsCurrent` and `projectionWarning` describe that
second stage. `error` remains the authoritative-operation failure channel.

Recovery acceptance follows the same rule: a true `ingest` result means media
promotion, canonical state, receipt and the move to Accepted committed. A later
report failure is returned separately and logged against the acceptance event.
`ingestPending` counts that acceptance and appends its projection warning to a
separate list, not to retryable Pending failures. A genuinely uncommitted next
package still fails normally; this change does not bypass initialization,
transaction recovery, validation, locks or filesystem checks.

The existing journaled `projections-dirty.json` marker survives report failure.
Fix the blocked generated-report destination, preserving any unrelated file or
directory there. Rebuild views from committed state with:

```text
archive-cli rebuild-projections <archive-root>
```

Normal initialization also repairs a dirty projection when its destination is
usable again. Neither route repeats discovery, re-promotes media, changes an
Accepted receipt, or appends another acceptance/history event. No archive data
or user-created obstruction is deleted automatically to make a report writable.

## CLI compatibility

Existing command forms and result fields remain. Scan adds `committed` and
`projections` fields; import adds `warnings`. Diagnostics describe committed work
explicitly. Exit codes are:

| Code | Meaning |
| --- | --- |
| 0 | Requested operation and generated reports succeeded. |
| 1 | A requested authoritative operation, initialization, or explicit report repair failed. An import batch can still report earlier accepted packages. |
| 2 | Invalid CLI arguments, unchanged. |
| 3 | Incomplete discovery, unchanged, including when the same scan also reports dirty projections. |
| 4 | A complete scan or otherwise successful import batch committed, but generated reports need rebuilding. Do not resubmit accepted packages. |

The GUI shows `COMPLETED WITH WARNINGS`, preserves accepted/observed counts, and
explains report-only recovery. A later health refresh may still show the blocked
projection as unhealthy; it does not change the recorded operation outcome.
Mixed batches retain failures and warnings separately, and cancellation retains
its existing stop-at-boundary behavior.

## Regression evidence

Two new hardening cases and two real-media CLI integration tests reproduced the
old false-failure behavior before the correction. They block only a generated
catalog path in a temporary initialized archive, assert durable state and package
placement, and compare registry/history/receipt/media bytes after repeated
report-only recovery. The actual-widget regression exercises the asynchronous
Pending-import action and verifies accepted count plus warning classification.
The complete existing suite remains enabled. Exact commit, local/sanitizer/CI
results and integration status are recorded in issue #3, not inferred from this
document. Frozen audit evidence remains unchanged.
